# 30 · 调度自检与数据质量处置

> 状态：V2.0.0 增量（2026-11-21）。本文说明启动/周期调度自检、数据源备用链、质检修复与验收失败说明的运行口径。

---

## 1. 调度自检

### 1.1 计划来源

所有作业的计划、分组、依赖与启动策略集中在 `backend/app/jobs/plan.py` 的 `JOB_PLANS`；APScheduler 的触发器、系统状态页的「计划」列和 supervisor 都读同一份注册表。`validate_registry()` 与测试会校验 `JOB_PLANS` 与 `backend/app/jobs/runner.py:JOBS` 不漂移。

### 1.2 逾期判定

- **定点作业**：取最近一个已到点的计划时刻（多定点取最近）；`last_run_at` 早于它即逾期，超过 `max_lag_hours` 则跳过并写原因。
- **间隔作业**：`last_run_at` 为空或 `now - last_run_at > 周期 + grace` 即逾期；`grace = min(600, max(60, 周期×0.1))`。
- 禁用、运行中、`startup=false`（`backfill_history`/`timeline`）在启动自检中跳过。

### 1.3 启动/周期编排

`backend/app/jobs/supervisor.py:run_schedule_check()`：

1. 数据阶段：按顺序补 `collect_quotes` → `collect_daily_bars` → `collect_rates` → `collect_macro` → `collect_calendar` → `collect_positions` → `collect_gold` → `collect_news` → `collect_news_slow` → `collect_bodies`，以及 `check_data_quality`/`repair_data`。
2. 数据就绪：日线关键标的齐全且最新 ≤10 天、宏观关键序列在频率窗口内、行情快照 ≤3 天且覆盖 ≥20 个标的。
3. `blocked` 时按失败维度重试一次采集；仍不就绪则下游写 `JobRun(status="skipped")` + `blocked_by`，不硬跑。
4. `ok/degraded` 时按依赖补 `analyze → cycle → lenses → decide → theses → ledger → brief_*`、`score_predictions`、`scan_alerts` 等。
5. 每次自检落 `schedule_checks`，报告包含 `readiness/jobs/retries/blocked`；`GET /api/system/schedule-check?limit=1` 可读，`POST` 可手动触发。

启动后默认 60 秒执行（`EPIC_SCHEDULE_STARTUP_DELAY_SECONDS`）；另有一个每 15 分钟的周期自检，正常调度下是 no-op。

## 2. 数据源备用

- 备用链注册在 `backend/app/ingest/chains.py`；`failover.run_chain()` 按主源→备源尝试，每次尝试写 `source_health`。
- 连续失败 ≥3 次（`EPIC_SOURCE_FAILOVER_FAILURES`）且最近失败在 15 分钟内，该源进入冷却（`EPIC_SOURCE_FAILOVER_COOLDOWN_MINUTES`）；主源冷却时直接走备用；全部候选冷却时允许最高等级源试一次，避免永久锁死。
- 全部失败时保留旧数据并标 `stale`，不写占位值；`/api/system/sources` 显示 `roles/domains/last_success/consecutive_failures/success_rate_24h/cooldown_until` 与 `chains`。
- FRED 作为美债、SOFR/EFFR、H.4.1、H.6 的备用源（keyless CSV）；主源缺失或滞后时才补，不覆盖新鲜主源数据。
- 实测 Stooq 返回 JS 反爬挑战、Yahoo 返回 429，因此市场数据继续用新浪/东财/腾讯互备，不接入这两个源。

## 3. 质检与修复

### 3.1 批次与结构

`check_data_quality` 每轮生成一个 `batch_id`；`DataCheck` 增加：

- `severity`（info/warn/error/critical）
- `cause` / `impact` / `remediation`
- `action_job`

`backend/app/ingest/quality.py` 负责分类；`latest_batch()` 保证 API/验收/告警/简报读同一批，键为 `kind:dataset:symbol`。

### 3.2 修复

`backend/app/jobs/repair.py:run_repair()` 读取最新失败批次，去重 `action_job`，跳过禁用/运行中/冷却期作业，单轮最多 3 个（`EPIC_AUTO_REPAIR_MAX_ACTIONS`），冷却 30 分钟（`EPIC_AUTO_REPAIR_COOLDOWN_MINUTES`）。冷却按 `repair_attempts` 里该作业上一次**修复尝试**计时，而不是 `jobs.last_run_at`——刚跑完并写出坏数据的采集作业仍会被重跑修复。实际执行过修复后默认再跑一次 `check_data_quality` 复核。手动入口：`POST /api/system/data-quality/repair {"recheck": true}`。

### 3.3 质量门控

`backend/app/platform/quality_gate.py:assess()` 返回：

- `ok`：最新批次通过且关键数据新鲜。
- `degraded`：非关键失败、批次 >36h、覆盖不足；允许出结论但降置信度。
- `blocked`：关键检查失败、日线/宏观实质上不可用；透镜组合 `actionable=false`，决策不删除旧计划并返回跳过原因。
- `unknown`：尚无质检批次。

透镜最终 confidence 夹在 `[0.3, 0.85]`；周期/分析/黄金把门控写入 `degraded_reasons`。

## 4. 验收失败说明

`/api/system/acceptance` 由 `backend/app/platform/acceptance.py` 实时计算。每个检查包含：

`id/name/category/status/severity/passed/required/actual/detail/reason/impact/remediation/action_job`。

- 无质检批次 → `quality.latest_batch=fail` 且说明「尚未运行数据质检」，不再假通过。
- 批次 >36h → fail 并给出过期小时数。
- 关键链全断/调度逾期/数据不就绪 → fail，并附最近作业/源错误线索。
- `warn` 不使 `passed=false`；`failed_summary` 汇总失败项与 hints。

前端「系统状态 → 验收自检」显示失败摘要、实际/要求、原因/影响/处置，并可点击 `action_job` 触发修复。

## 5. 新接口

| 接口 | 用途 |
|---|---|
| `GET /api/system/schedule` | 实时逐作业计划/到期/逾期/动作 |
| `GET /api/system/schedule-check?limit=1` | 最近自检报告与实时计划 |
| `POST /api/system/schedule-check` | 手动自检（`wait=true` 同步；`dry_run=true` 只报告） |
| `GET /api/system/quality-gate` | 全局质量门控 |
| `GET /api/system/data-quality` | 最新质检批次的严重度/原因/影响/修复 |
| `POST /api/system/data-quality/repair` | 手动修复（`recheck` 可复核） |
| `POST /api/system/jobs/{name}/run` | 手动运行白名单作业 |
